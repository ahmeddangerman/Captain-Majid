# Shot flow trace from the Japanese ROM

This is a direct instruction trace from the verified Japanese ROM. The external disassembly was used only to locate routines; the notes below were checked against the ROM bytes with a 6502 disassembler.

## Confirmed order

1. The action caller at `$8298` prepares an attacking move through `$C54B` index6 and `$819D`, then runs energy/action power at `$8F72`. The native `prepare_attacking_action` now joins supplied profile/move content, side-specific stamina and action power.
2. With no selected defenders (`$0600 == 0`), it stores result code 0 at `$82AA` and enters the next result dispatcher.
3. With defenders, it iterates the records in `$0601...` at `$82B6–$82EF`. Each selected defender runs through `$8349`, which invokes energy handling at `$8FF3`, chooses action/defender threshold data, then calls the comparison at `$8EE9`. On every pass through `$82FC`, the loop reloads that defender's subtype from `$0606,X` into `$043E` at `$8309–$8312`; if the result is 0/1, `$83BC–$83CE` advances to the next record and returns through `$82FC`.
4. The result code is stored at `$8148`. Codes 0 and 1 advance to the next selected defender at `$83BC–$83D1`; codes 2 and 3 leave the loop and enter the result dispatcher at `$83F5`.
5. The keeper comparison is a separate later route at `$854A–$856B`, followed by the story override and keeper result handlers. It is not safe to apply it after every field-defender comparison.

The complete attacking stage now has a banked differential trace: original `$8F72` calls the real move/profile loader, restores its PRG banks, applies energy and rolls power. It matches3,882 constructed native cases without skipped calls. This covers the attacker stage; the remaining field/keeper continuation still needs a joined original trace. See [BANKED_ATTACK_TRACE.md](BANKED_ATTACK_TRACE.md).

## Integration boundary

The call to `$C54B` with index 7 before `$8349` is the per-defender data preparation path: `$CE6E` switches to PRG banks 28/29 and calls `$8224`. It loads the selected field player's skill/move strength, move effect, and stamina cost before energy handling. The native standard-skill loader and contact wrapper now reproduce that preparation with decoded profiles and replaceable content. Its complete original-ROM comparison passes 16,064 fixtures. [FIELD_DEFENDER_PREPARATION.md](FIELD_DEFENDER_PREPARATION.md) records the remaining profile/content and scheduling boundary.

`resolve_prepared_field_contacts` now connects supplied player profiles, selected moves, defensive energy use, and comparisons in this order, returning an updated roster without mutating its input. Its tests cover current stamina bytes in profile lookup, primary record type in surcharge selection, and stopping before later defenders. Original variation/threshold selection and a full-loop ROM comparison remain pending; see [PREPARED_DEFENDER_SEQUENCE.md](PREPARED_DEFENDER_SEQUENCE.md).

The native `calculate_defender_contact` reproduces one comparison and its code-1 power loss. `resolve_field_contacts` applies caller-selected contacts in order, carries forward power, starts each contact with that defender's input subtype, continues on codes 0/1, and stops on codes 2/3. This matches the ROM loop, which reloads `$0606,X` into `$043E` before each defender. The selector at `$E4D7` now reproduces the ROM's ordered nearby-player IDs, side-specific limits, status-byte skip, and strict square-radius check. Its callers still supply the radius, and later contact parameters remain explicit. `resolve_field_contact_handoff` sends the resulting code to the existing outcome handler, including optional ordinary ball recovery for code 2. Codes 0/1 remain `continue_action` for their later caller-specific phase. `resolve_action0_shot_continuation` connects caller-supplied post-contact power/subtype and the verified action-0 route gates to the existing keeper calculation and outcome handler. The older direct `resolve_explicit_shot` path remains available for an unconditional, caller-selected keeper attempt.

`resolve_prepared_field_shot` now joins the prepared roster/contact sequence to the field handoff and gated action0 keeper route. It dispatches with the last visited defender and carries remaining shot power while preserving separate attacking and defensive subtypes. Native integration checks cover goal/save/recovery and terminal possession routes. Attacker/keeper preparation, original table selection and full gameplay trace remain pending.

The `$83F5` indirect table sends codes 0/1 to `$8408`, code 2 to `$843F`, and code 3 to `$844B`.

- Codes 0/1 enter the selected action continuation at `$8408` and dispatch on `$043B` through the inline table at `$841D`: actions 0/1 go to `$8429`/`$DE52`, and actions 3/4 go to `$E54C`/`$E596`. Action 2 reaches a self-loop at `$843C`. The action-0 entry at `$8429` checks the post-loop `$0617` active-defender count/flag: a nonzero value jumps to `$88F3`; zero clears `$0621` and enters `$DCFD`. From there, one branch enters the loose-ball path at `$8BE5`. Otherwise `$DD1C` selects the opposing goalkeeper (ID 0 or 11) and checks its +10 status field: nonzero goes to `$88F3`, while zero reaches `$84F8`, which prepares one opposing defender and proceeds through `$8FF3` to the keeper comparison at `$854A`. Action 1 has a separate player/ball continuation at `$DE52`. The keeper handoff is therefore conditional on the action-0 continuation, rather than implied by result code 0/1 alone.
- The native action-0 continuation accepts only field result codes 0/1. It returns a separate route for unsupported actions, a nonzero post-loop `$0617`, the `$8BE5` loose-ball branch, or nonzero opposing-goalkeeper +10 status. Only when the action code is 0 and all gates allow it does the helper supply post-contact power to keeper comparison and pass its result through the existing goal/save handler. The attacking subtype feeds the outcome handler; the keeper retains its separate defensive subtype. The caller still supplies these gate values and gameplay inputs explicitly.
- Code 2 runs the defender experience helper and goes through `$8BDF`. That routine adjusts ball coordinates, checks for a direct field-player capture, and otherwise chooses an available player by expanding the search radius. Its ordinary interior-field handoff updates the ball owner and possession side at `$8E6E`/`$8C12`.
- Code 3 awards defender experience, then branches by the selected defender. Defender IDs 0 and 11 are keepers and transfer possession directly to that keeper's side. A field defender transfers possession when defense action is 2. Other field-defense actions enter a separate animation/continuation path without an immediate possession write.

The native `resolve_defender_outcome` now records these handoffs. The new `resolve_field_contact_handoff` composes it with the ordered contact sequence: result 2 can invoke the ordinary interior-field recovery, result 3 can transfer control to a keeper or field player, and results 0/1 preserve ownership for the next phase. The immediate code-3 possession writes matched 144 original-ROM cases; ordinary code-2 recovery matched 512. Recovery requires the ball update to be inactive and does not handle boundary restarts. The other code-3 animation path still has no immediate possession update. The original nearby-defender selector now matches 1,024 ROM cases, but player attributes, action-specific defense values, and threshold/variation-table loading still come from explicit caller inputs.

## Evidence boundary

This trace establishes call order, loop exits, and the ordinary interior-field recovery handoff. It does not yet reproduce complete screen/action setup, content selection, event messages, rewards, animations, active-ball movement, boundary restarts, match clock, or a full gameplay trace. The native TCP fixture also remains a contact-loss demo rather than a match session.
